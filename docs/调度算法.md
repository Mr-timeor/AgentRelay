# 当前调度算法

当前算法是**依赖与资源约束下的贪心列表调度，加连续任务链融合**。完成事件驱动实际推进，排序依据是当前任务图和执行状态。算法没有工期预测模型，也不承诺全局最优。

## 1. 找到真正就绪的任务

先诊断缺失前置、未知产物和依赖环。任务只有在pending、已授权、硬前置满足且资源可用时进入就绪集；暂停时不启动新任务。

任务依赖要求上游completed；产物依赖要求对应output已accepted。只使用实际状态，不把未来计划算作交付。资源按项目相对文件/目录匹配，读读可并行，写入与重叠读写互斥；未结束或unknown运行仍保留占用。这是协作声明，不是文件系统隔离。

## 2. 排序并贪心分配

就绪任务依次比较以下条件。

1. priority数值越小越先。
2. 同优先级时，依赖图上可达的全部后代任务越多越先。
3. 再按ID的localeCompare顺序兜底。

后代数量统计图中全部可达的间接和直接后继，用于优先推进影响范围较大的任务。这一结构指标与任务耗时、关键路径和本次立即解锁数量无关。

全局规划按agents配置顺序，为空闲成员选择第一个owner/category匹配、未被预留、与已选首任务无资源冲突的就绪任务。实际dispatch/next则针对指定成员重新规划，其他成员的建议不会占走该成员可做的任务。没有额外的上下文成本、速度或负载均衡模型。

## 3. 沿连续依赖链融合执行段

从选中的首项开始，在虚拟状态中推演它已完成，再找同一个成员能承担、直接依赖上一项且此时就绪的后续任务。分支按priority、ID选择，不再使用后代数量排序。

遇到review检查点、没有满足条件的可接续项，或maxSegment上限时停止。默认maxSegment为4。类别本身不是执行段边界；跨成员消费者被记录为中间交付点，交付可解锁其他成员，原成员仍可继续自己的链。

例如，在A1→A2→等待B3→A3→A4这条链中，B3未交付时，A的建议段只包含A1、A2，交付后再计算后续。虚拟完成只用于建议，实际状态与资源占用在逐项执行时更新。当前贪心延伸不保证找到最长链或全局最佳划分。

## 4. 按真实事件逐项执行

dispatch启动并占用当前一项，segment后续项提供执行建议。成员完成后再next，重新检查真实前置与资源。report交付以及accept、approve、resume、追加任务和调整未派发任务等管理动作会触发自动派发检查。

开启autoDispatch时，已登记waiting的成员若有任务就收到消息；DSH可恢复已自然卸载成员的原Session。当前成员若仍在回合内，可自行next连续领取。没有持续模型轮询或后台定时调度。

当前每次plan都会重新诊断、扫描、排序并构造执行段。未知投递保留占用，失败后由Lead显式处理。

## 5. 适用范围与验证

当前实现适合范围明确、依赖可表达的小规模开发和测试任务图。仓库提供串行链、分叉汇合、跨类别依赖、共享资源、交付检查点和授权失败等[合成任务图](../fixtures/benchmarks)，以及可重复运行的[离线评测方法](离线评测.md)。

评测比较总完成时间、等待、派发及约束违规等结果。真实项目中的效率、费用和上下文收益仍需分别测量。实现入口见[planner.ts](../src/core/planner.ts)、[scheduler.ts](../src/dispatcher/scheduler.ts)、[adapter.mjs](../harness/adapter.mjs)。
