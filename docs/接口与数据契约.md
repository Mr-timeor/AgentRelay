# AgentRelay 接口与数据契约

本文描述当前源码的任务格式、调度核心和Harness工具接口。安装方法见[快速开始](快速开始.md)。

## 输入与默认值

任务和执行者都需要 `id`。完整例子见[开发测试任务](../fixtures/development.json)。

| 字段 | 用法／默认 |
|---|---|
| title、category | 默认任务ID、general |
| dependsOn | 默认空；字符串表示任务完成前置，`{taskId, output}` 表示产物交付前置 |
| resources | 默认空；相对路径字符串表示写入，也可指定 `{path, mode: read或write}` |
| outputs | 要交付的产物名称，默认空；提交时给文件、提交或接口引用 |
| priority | 默认2，越小越优先 |
| owner | 可选，限定执行者 |
| specFile | 可选，项目相对任务卡引用，可带#章节；省略/null/空字符串不提供，不读取全文 |
| review、approval | 默认false；分别表示交付后验收、启动前授权 |
| agents[].categories | 默认空表示通用执行者 |
| maxSegment | 默认4；执行段任务数量上限 |

当前支持任务完成和产物交付两种硬前置。只有实际完成或接受的结果可以解锁下游。耗时不参与当前算法，无需填写。

## 按需启动

DSH bundle 默认 `onDemand:true`。安装启用后处于待机，仅注册 `scheduler_manage`，不绑定Lead，也不读取或创建任务文件。该流程已通过 Desktop 0.2.1-rc.3 的隔离 CLI 安装、冷启动和本地mock工具闭环验证；自然语言到工具的模型选择未在本轮实测。

| 动作 | 参数与结果 |
|---|---|
| load | 可选workspace绝对路径，省略时使用当前会话工作区。绑定Lead，返回规划指引、startup和paths |
| prepare | project为完整项目JSON文本，包含name、agents和tasks。保存新任务和状态、生成HTML，返回agents、agentCount和waitingForAgents |
| prepare恢复 | 省略project读取已保存计划，已有任务与状态文件保留 |
| unload | 没有未结束运行且其他工具调用已结束时关闭本次存储与图更新，保留文件和历史，再回到待机 |

默认paths为工作区下的`.scheduler/tasks.json`、`.scheduler/state.json`和`.scheduler/flow.html`，可在插件配置中指定其他路径。主插件在prepare后维护HTML，默认按需模式直接使用该图。

用户说“加载调度器”后，由当前模型调用load并根据需求规划任务和专项分工。成员数量来自Lead生成的agents列表，算法按现有成员与任务关系安排工作。

prepare后状态暂停，Lead按agents逐一spawn。该动作通过宿主团队服务创建子会话，默认 `fresh` / `spawn`，不复制父聊天历史；仅复用当前团队内同名成员，不接管手动新建的普通对话。专项成员阅读计划，再调用`scheduler_next({readySummary:"分工说明与已就绪"})`登记回复。只有计划内真实成员的就绪摘要计入准备人数，创建会话本身不算就绪。全部成员就绪后进入running并启动既有自动派发，部分成员回复时继续waiting。

成员创建、通信和原有子会话恢复由 Harness 提供；插件保存任务状态、交付与返工记录，并据此触发调度。必要要求应写入计划或任务卡，不能假设子代理已看到完整 Lead 聊天。

startup返回当前phase、成员列表、数量、已就绪与待就绪成员和回复摘要。阶段主要为standby、planning、waiting和running。重启或unload后重新加载、准备并建立就绪登记，历史运行仍保存在状态文件中。

固定项目兼容模式使用`onDemand:false`，配置projectFile和stateFile，沿用原来的首次调用绑定与autoDispatch设置。独立view bundle用于固定项目时也设置`onDemand:false`，并配置projectFile、stateFile和graphFile。

## 程序接口

| 接口 | 作用 |
|---|---|
| normalize、diagnose、plan | 规范化、图诊断、就绪集合与执行段；不修改事实 |
| FileStore.open、snapshot、change、close | 进程内串行保存JSON，跨进程独占写锁，保留上一版 `.bak` |
| Scheduler.dispatch(agentId, send) | 保存当前任务占用和委托，再调用传输函数一次 |
| delivery(run) | 只读生成当前委托上下文，按当前任务重建建议段，不重新派发 |
| acknowledge(agentId, ids) | 确认对应运行；重复回执不增加运行记录 |
| report(agentId, ids, report) | checkpoint、completed、blocked、failed与摘要、产物引用，可选files/tests证据 |
| accept(taskId, output?) | 接受指定中间产物或整项待验收任务 |
| rework(taskId, feedback) | 退回待验收任务，保留已接受产物，保存旧报告及反馈，新一轮继续未完成部分 |
| control(action, taskId?) | pause、resume、approve、retry、resolve-stopped |
| addTasks(tasks) | 校验后追加新任务，不修改已执行任务 |
| updateTask(taskId, changes) | 修改从未派发的pending任务，校验后保存并记录变更字段 |
| expire(now?) | 将超过回执等待时间的委托标为unknown |
| renderGraph(state) | 输出只读HTML/SVG快照 |

`dispatchId / attemptId / permitId` 由程序生成并保存在同一个Run中。模型传 `dispatchId`，适配器补齐内部回执关联。

`new Scheduler(store, receiptTimeoutMs?, workspace?)` 的第三参用于解析显式文件证据，默认当前进程目录。Harness 适配层传入绑定的会话工作区，独立调用者应传入实际项目目录。

## 状态与交付

任务状态包括pending、running、review、completed、blocked和failed。Run另记awaiting、active、unknown和finished。running表示任务已被占用，显示时进一步区分待回执、执行中和待对账。

普通任务按执行者报告接受，摘要应写明检查依据，测试结果由开发和验收流程核对。配置 `review: true` 的任务等待Lead验收。中间产物可独立提交和验收，下游可据此提前开始。

交付时的`outputs`是名称到引用的对象。引用可以是非空字符串，也可以是非空字符串数组，兼容历史多路径交付；路径、提交、URL和其他引用原样保存，不自动读文件。空值、纯空白、混合数组或错误映射在提交前拒绝。

已接受产物再次报告相同引用时保留接受状态；不同引用会拒绝整份报告，原进度、历史与已启动下游保持。数组按原类型、顺序比较。未接受的草稿仍可更新，已接受交付的修订使用新增任务。`accept`也校验本次尚未接受的旧引用；不迁移或撤销历史已接受项。仅提交引用时，规则保护引用记录，不读取引用指向的内容。

v0.1.1 提供可选 `files:{产物名:相对路径或路径数组}`。调度器实际读取所声明的工作区文件，保存 `files:[{path,size,sha256}]`；拒绝缺失文件、目录及越过工作区的实际路径。显式 `accept` 会重新读取对应文件并对照指纹，内容变化时只拒绝本次验收。普通任务仍按报告完成；不增加审批，也不自动撤销已解锁下游。已接受产物不能事后补写或替换证据；旧状态没有files时仍按引用模式处理。

可选 `tests:[{command,exitCode,stdout?,stderr?}]` 保留命令、整数退出码及日志引用，记录加 `source:"reported"`。这是执行者自报，调度器不执行命令、不读取日志，也不按退出码自动改写任务结果。含产物的回执在当前Run的outputs留下提交快照，tests随回执追加；返工仍保留旧Run和文件证据。

暂停只停止新任务；执行者提交blocked或failed表示本轮工作已停止，释放占用。失联／未知不自动释放，Lead确认停止后使用resolve-stopped。失败后显式retry保留已接受产物、清未接受草稿，以新运行继续剩余工作，旧记录保持；已接受引用本身需要修订时新增任务。

Lead可用rework退回`review:true`且当前待验收、没有未结束运行的任务，feedback须写明具体修改要求。任务回到pending，保留启动授权和已接受产物，只清未接受草稿。旧Run保持finished，附可选`rework:{feedback,outputs}`保存当时全部引用及接受状态，原summary和历史保留。新Delivery的rework附previousAttemptId、feedback及旧快照。保存范围为历次被退回提交时的报告与产物引用。

Delivery在当前任务已有接受交付时，附可选`acceptedOutputs:{产物名:引用}`，指示新轮继续剩余工作。已接受引用同值重报时保留接受记录，异值重报时拒绝提交。新轮完成后按review设置验收。

## 宿主工具

- `scheduler_status(taskId?)`：规划期间返回启动进度，准备后空参返回概览、方案及startup。摘要最多300个Unicode字符（含省略号），附原长、截断标记及必要的summaryRead，runs不重复带summary。传taskId读取该任务定义、完整progress及最近一次run元数据。详情不检查回执到期。按需模式由prepare初始化状态，固定项目模式保持首次服务调用的创建或恢复行为。
- `scheduler_next(dispatchId?, readySummary?)`：准备期间用readySummary回复分工与已就绪，返回waiting。开工后收到委托时确认，当前项结束后空参领取下一项并同时确认。有任务时统一返回Delivery（含task、startedAt、phase:active、可选specFile及dependencies），无需再次回执，没有任务时返回waiting。
- `scheduler_report(dispatchId, summary, status?, outputs?, files?, tests?)`：默认completed；outputs、files与tests分别为可选JSON文本。
- `scheduler_manage(action, target?, workspace?, project?, output?, feedback?, tasks?, tasksFile?, changes?)`：仅Lead。按需模式用load、prepare、unload管理启动过程，其他动作可创建专项成员、派发、追加或调整未派发任务、验收、退回返工、授权、暂停和对账。rework时target为任务ID、feedback为具体反馈。

有返工历史时，指定任务的status详情额外返回reworks数组，每项含attemptId、原summary、feedback和当时的outputs。指定任务详情的最近Run可带提交outputs与tests，概览和Delivery不重复携带整份运行证据。概览不带reworks数组；旧状态缺少新增字段时继续读取。

由 `exec.agent` 取得身份，只允许配置的Lead团队。工具不调用原生任务板，不要求模型手填身份、版本或资源锁。

Delivery.dependencies只包含直接前置。指定产物依赖给output/reference，普通任务依赖给已接受产物的outputs映射。同一上游摘要只带一次，交付副本最多300个Unicode字符，截断加省略号，原state/history保留完整内容。任务卡与产物通过引用交接，执行者按需读取。

add-tasks使用tasks或tasksFile二选一。tasks传单任务对象或非空数组的JSON文本，tasksFile传独立JSON文件路径，相对projectFile所在目录，也接受绝对路径。校验成功后保存新任务并触发wakeReady，返回revision、added及可选wakeups。追加成功后若唤醒失败，已保存的任务继续保留。新任务沿用pending和approval逻辑，无效图或空数组在保存前拒绝，既有任务、产物与历史保留。

update-task由target指定现有任务，changes传JSON对象文本，可改title、specFile、dependsOn、owner、resources和priority。依赖和资源数组整体替换，owner/specFile用null或空字符串清除。任务须pending且没有任何历史Run。已配置`approval:true`的任务修改后重新待授权，普通任务沿用默认授权状态。校验与派发沿同一存储队列执行，保存后按既有规则wakeReady。任务JSON保留为初始化输入，更新计划存在state内。该入口已通过隔离宿主配本地mock验证。

```text
scheduler_manage({action:"update-task", target:"Q2", changes:'{"owner":"tester","dependsOn":["A1"]}'})
scheduler_manage({action:"rework", target:"A2", feedback:"请保留已接受契约，补充错误输入处理"})
```

## 自动派发

按需模式在全体成员就绪后自动推进，准备期间的手动派发、resume和普通next均不能提前开始任务。固定项目模式的autoDispatch默认false，开启后成员首次next可领取就绪任务。

next无任务时按持久成员name/id登记等待。真实report提交和accept/approve/resume等管理动作后，插件按既有依赖及占用给等待成员派发。report/manage返回wakeups摘要，status增加autoDispatch、waitingAgents（live）和inactiveWaitingAgents（已卸载逻辑等待），沿用四个工具。成员自然卸载后继续保留等待意图，通过原生消息恢复同一Session。持久成员失败或缺项由Lead处理。传输失败保留unknown，不撤销上游完成、不重发。

Scheduler.plan(agentId?)支持仅规划指定成员。dispatch在串行状态提交中对指定成员重新检查前置、能力、授权及资源，其他空闲成员的建议预留只用于展示。等待集合仅在进程内，重启后需重新next或手动派发。

WakeQueue合并同时触发的后续扫描，当前一轮加至多一轮已排队补跑，补跑采用最新触发上下文。状态提交与历史分别保存，共用补跑的调用会共享其wakeups摘要。

## 必要边界

状态写入成功后才投递；发送未知不重发。回执阈值默认120秒，发送响应有超时计时；回执超时在查询／领取时检查，不另起后台服务。重启时未结束运行进入unknown。

单项目支持一个写进程：读取或初始化状态前独占创建 `<状态文件>.lock`，记录PID、token和时间；第二进程明确拒绝，同进程重复打开也拒绝。真实路径归一化覆盖常见junction别名。锁只约束采用新版FileStore的写者，不能约束旧副本或人工直接改文件。路径占用协调共同遵守声明的执行者，实际文件操作仍由项目流程负责。状态文件保留上一版`.bak`，用于出现文件问题时人工检查和恢复。

FileStore.close等待已排队提交后释放自己的锁，且可重复调用，关闭开始后拒绝新修改。初始化失败释放已取得的锁；异常退出保留残留锁，确认旧写者已结束后人工移走，不按时长自动抢锁。只读图和CLI查询不取写锁；图可创建状态父目录用于监听，但不创建或写入状态文件；CLI导图拒绝输入输出同路径。

## 用量与防循环

请求数、token、费用和总时长只作记录，不设预算上限，不据此阻止派发或判定任务失败。拿不到的用量记unknown。

保留DAG循环诊断、完成运行不可重做、unknown不自动重发和失败后显式retry。next返回waiting后执行者结束本回合，Lead不轮询空等；同一操作没有新信息或状态变化时停止重复，报告阻断，等新交付或明确调整后继续。

其中“不重复空等”是执行说明中的行为规则，当前没有通用的模型调用循环自动检测器。回执超时用于标记失联委托，maxSegment用于划分执行段，均不作为预算限制。
