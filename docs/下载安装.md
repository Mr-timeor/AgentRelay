# 下载包安装说明

本说明适用于已经构建好的插件 ZIP。下载者解压后即可安装其中的本地 bundle，无需克隆源码、安装 npm 依赖或重新构建。独立运行包内 CLI 时需要 Node.js 22 或更新版本。

使用支持本地 bundle 安装和 agent-team 服务的 DeepSeek Harness。已有 Windows Desktop 0.2.1-rc.2 的接入记录及 0.2.1-rc.3 的小规模真实协作记录，其他版本需核对宿主接口。下载包的实际安装验收状态以随包发布信息为准。

## 1. 下载并解压

下载插件 ZIP 和同次发布的 SHA256 校验文件。可在 PowerShell 中核对 ZIP 的哈希，再解压到要保留的目录。

```powershell
Get-FileHash -LiteralPath 'D:/Downloads/插件包.zip' -Algorithm SHA256
```

命令中的 ZIP 路径请替换为实际下载文件。把输出的 Hash 与校验文件中对应 ZIP 的 SHA256 比较。

ZIP 顶层目录形如 `dynamic-task-scheduler-0.1.0`。下文的 `<解压目录>` 指这一层目录，里面包含以下内容。

```text
<解压目录>/
  安装说明.md
  harness/
    bundle/             # 调度器，本地安装时选择此目录
    view-bundle/        # 可选流程图，本地安装时选择此目录
  core/dist/            # 独立规划与命令行
  examples/
    desktop.patch.yml   # 配置示例，填写项目路径后使用
  fixtures/
    development.json   # 开发与测试任务示例
  manifest.json
  LICENSE
```

两个 bundle 各自含有 `package.json`、`index.mjs`、`cordis.patch.yml` 和编译后的 `dist`。安装入口是这两个子目录。ZIP 外层目录用于容纳说明、示例和独立核心，当前步骤采用解压后的目录安装。

## 2. 准备项目与配置备份

在目标项目中准备一个新的 `.scheduler` 目录。首次接入可以把包内 `fixtures/development.json` 复制为项目的 `.scheduler/tasks.json`，再根据实际需求修改任务。

本例使用 `D:/projects/my-app` 作为项目路径。准备后的目录形如以下结构。

```text
my-app/
  .scheduler/
    tasks.json       # 任务定义
    state.json       # 首次查询插件时创建
    flow.html        # 图插件导出
```

已有项目应使用自己的任务定义和对应状态文件。首次试装选择新的 `stateFile` 路径，便于核对初始状态。

保存当前 Harness profile 的配置备份。已经安装过调度器或图插件时，同时记录原有插件的安装位置与启用设置，便于恢复。

## 3. 安装两个本地 bundle

在所用 Harness 的本地插件安装通道中，通过 `plugin_manager` 的 `install_bundle` 安装 `<解压目录>/harness/bundle`。需要流程图时，再安装 `<解压目录>/harness/view-bundle`。具体调用参数以该宿主版本显示的工具说明为准。

安装结果应包含 `dynamic-task-scheduler`，可选图插件对应 `dynamic-task-scheduler-view`。两个 bundle 自带的装载行初始为 `disabled: true`，接下来填入项目配置后启用。

这些插件使用 Harness 提供的依赖，安装位置由宿主 profile 管理。无需在解压目录运行 `npm install`。

## 4. 填写项目路径并启用

参考包内 `examples/desktop.patch.yml`，在所用 profile 的 `cordis.patch.yml` 中加入或调整下面的配置。把所有 `D:/projects/my-app` 路径换成目标项目的绝对路径。

```yaml
- insert:
    - id: agent-team
      name: '@deepseek-ai/dsh-experimental-agent-team'
      config:
        maxMembers: 8
        maxTasks: 256
        maxMessageBytes: 65536
        disposalTimeoutMs: 5000
- id: dynamic-task-scheduler
  disabled: false
  config:
    leadSessionId: auto
    autoDispatch: false
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
- id: dynamic-task-scheduler-view
  disabled: false
  config:
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
    graphFile: 'D:/projects/my-app/.scheduler/flow.html'
```

已有 agent-team 服务时使用现有服务。只安装调度器时省去图插件配置。按插件 id 覆盖装载行时填写 `disabled` 和 `config`，`name` 沿用 bundle 提供的值。

首次验证使用 `autoDispatch: false`。完整退出并重启 Harness，使安装文件和配置一同加载。

## 5. 验证加载与初始状态

在目标项目工作区新建一个将要负责调度的 Lead 会话。确认工具列表中出现以下四项。

- `scheduler_status`
- `scheduler_next`
- `scheduler_report`
- `scheduler_manage`

由该 Lead 调用一次 `scheduler_status()`。首次合法调用会绑定 Lead，并在状态文件尚不存在时初始化 `state.json`。使用未改动的 `development.json` 示例时，应看到以下结果。

- revision 为 0，五项任务均为 pending，ready 仅有 A1。
- `diagnostics` 为空，`runs` 为空。
- `autoDispatch` 为 false，两种等待成员列表为空。

再调用一次 `scheduler_status({taskId:"A1"})`，核对 A1 为 pending、已授权、尚无产物和运行。该详情读取用于检查工具接口。

安装了图插件时，在 Harness 文件预览中打开目标项目的 `.scheduler/flow.html`。图应显示相同的五项任务和 revision 0。支持 HTML 交互预览的宿主可搜索、缩放和查看详情。

以上验证只检查加载和初始化。真实开发、成员创建和测试执行在用户启动工作流程后进行，并使用宿主配置的模型。

## 6. 开始协作

根据真实项目填写任务要求、依赖、交付物和测试方法。需要自动推进时，把调度器配置的 `autoDispatch` 改为 true，完整重启后由新 Lead 重新核对项目。

Lead 创建任务定义中声明的专项成员。成员用 `scheduler_next` 领取、`scheduler_report` 交付，返回 waiting 后结束回合，由插件在条件满足时唤醒。配置了 `review: true` 的任务，由 Lead 检查真实交付和测试依据后接受。

完整工作流程和工具示例见 [项目快速开始](https://github.com/Mr-timeor/Multi-Agent-Dynamic-Task-Scheduler/blob/main/docs/快速开始.md)。

## 7. 撤回本次接入

先确认本项目的专项成员已经停止。恢复安装前保存的 profile 配置，再通过宿主插件管理通道禁用或移除本次安装的 bundle。已有旧版本时恢复原安装位置与配置，最后完整退出并重启 Harness。

项目的任务定义、状态与业务产物由使用者自行保存。切换回原项目后，通过其 Lead 查询一次状态，核对任务和运行情况。
