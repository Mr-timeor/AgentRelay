# AgentRelay 快速开始

AgentRelay 用名单、任务依赖和交付规则组织 Harness 团队子智能体，用 HTML 任务图展示较复杂的开发与测试流程。成员创建、模型执行和会话恢复由宿主完成。

使用 v0.1.1 发布 ZIP 时，按安装说明完成配置和重启，直接从本文第 3 节开始。源码构建路径适合开发者，真实协作使用 Harness 中配置的模型。[下载安装](下载安装.md)

## 1. 获取源码并构建

需要 Node.js 22+、npm 和 Git。

```sh
git clone https://github.com/Mr-timeor/AgentRelay.git
cd AgentRelay
npm ci
npm run package:local
```

在项目根的 PowerShell 中读取构建目录。

```powershell
$packageInfo = Get-Content -LiteralPath '.scheduler/releases/latest.json' -Raw | ConvertFrom-Json
$packageRoot = $packageInfo.directory
$packageRoot
```

主插件位于 `$packageRoot/harness/bundle`，独立核心位于 `core/dist`，固定项目的可选独立图插件位于 `harness/view-bundle`。安装时使用对应 bundle 子目录。

v0.1.1 源码的 `npm run build` / `npm run build:view` 默认生成 `.scheduler/build/harness/` 下的插件，不再更新仓库内可能已被 junction 安装的旧副本。`npm run check:build` 校验不同构建入口的运行文件一致性。下载 ZIP 由源码重新构包，不能根据旧安装副本推断 ZIP 的版本。

只体验离线规划与流程图时，可以执行以下命令并用浏览器打开 `.scheduler/flow.html`。

```powershell
node (Join-Path $packageRoot 'core/dist/cli.js') graph fixtures/development.json .scheduler/flow.html
```

## 2. 安装并保持待机

先保存目标 profile 配置备份，完整退出 Desktop，再用宿主 CLI 安装。以下命令中的 profile 名称和路径替换为实际值，CLI 使用与 Desktop 相同的 DSH_HOME。

```powershell
dsh plugin --profile desktop add "<构建目录>/harness/bundle"
```

`dsh` 指宿主提供的 CLI，未加入 PATH 时使用其实际启动器路径。CLI 安装及冷启动已在干净测试 profile 验证。该安装方式可能建立指向 bundle 的 junction，安装后保留原目录。宿主支持时也可使用 `plugin_manager / install_bundle`，本轮未直接验证该 Desktop 工具调用。随后在 `cordis.patch.yml` 中配置 agent-team 服务并启用插件。

```yaml
- insert:
    - id: agent-team
      name: '@deepseek-ai/dsh-experimental-agent-team'
      config:
        maxMembers: 8
        maxTasks: 256
        maxMessageBytes: 65536
        disposalTimeoutMs: 5000
- id: dynamic-task-scheduler
  disabled: false
  config:
    onDemand: true
    leadSessionId: auto
```

已有 agent-team 服务时使用现有服务。`agent-team.maxMembers` 控制宿主的单团队创建上限。按插件 id 覆盖装载行时填写 `disabled` 和 `config`，`name` 沿用 bundle 提供的值。完整退出并重启 Harness 后生效。

默认待机仅提供 `scheduler_manage` 管理入口，不绑定 Lead，也不读取或创建任务文件。此模式由主插件在任务准备完成后维护 HTML 流程图。

## 3. 用提示词加载并告知任务

在目标开发项目的工作区中，向要负责调度的对话发送以下提示，然后补充真实需求。

```text
加载调度器。
我的任务是……
先按开发和测试两名专项成员规划，列出分工与数量。需要增加时先说明理由。
把任务依赖、文件范围、交付物和验收条件写进任务集，生成流程图。
让成员先阅读任务卡并回复分工与已就绪，全部回复后自动开工。
```

“加载调度器”由当前模型理解并调用工具。对应调用为 `scheduler_manage({action:"load"})`。宿主提供当前工作目录，也可显式传入 `workspace:"D:/projects/my-app"`。

`load` 绑定当前 Lead 并返回规划指引和文件路径。默认使用当前工作区的 `.scheduler/tasks.json`、`.scheduler/state.json` 和 `.scheduler/flow.html`，此时先完成需求规划。

## 4. 保存计划并创建团队子代理

Lead 将需求整理为包含 `name`、`agents` 和 `tasks` 的完整 JSON 文本，通过 `prepare` 提交。可以参考[开发测试模板](../fixtures/development.json)，按实际任务设置依赖、文件范围、产物和验收要求。

模板用两名成员完成五项任务。A1 交付接口后，开发继续做 A2，测试并行做 B1。B2 依赖两项交付，联合测试通过并经 Lead 验收后才解锁 A3。用 `dependsOn` 声明真正的前置，用 `resources` 声明要读写的路径，用 `specFile` 引用复杂任务的任务卡。适合由同一个人连续做的工作可以保留在同一专项会话里。

```text
scheduler_manage({action:"prepare", project:"完整项目 JSON 文本"})
```

`prepare` 保存任务定义，初始化状态并生成 HTML，返回专项成员列表、数量及等待就绪的成员。`agents` 是本轮计划名单，调度器的 `spawn` 只接受名单内成员。任务数量可以多于成员数量。提示词约束规划规模，DSH 的 `agent-team.maxMembers` 执行团队硬上限。

已有任务文件和状态时，用 `scheduler_manage({action:"prepare"})` 恢复保存的计划。已有文件保留，运行中的计划通过追加或调整工具更新。

Lead 按返回的成员名逐一创建团队子代理，例如模板中的两个成员。

```text
scheduler_manage({action:"spawn", target:"developer"})
scheduler_manage({action:"spawn", target:"tester"})
```

这里创建的是挂在当前 Lead 下的团队子会话，无需用户手动新建普通对话。仅当前团队内已有同名持久成员时，插件向原 Session 发送准备提示；独立普通对话不会按标题被接管。

从 Lead 会话头部的子智能体目录可打开实际成员，在支持的界面中也可选择“在侧边栏打开”。默认 `fresh` / `spawn` 不复制父聊天历史，必要要求应写进计划、任务卡或委托消息，后续执行保留成员自己的历史。创建完成只表示会话已建立，准备阶段的任务仍暂停。

每个专项成员阅读计划和自己的任务卡，再明确回复分工与就绪情况。

```text
scheduler_next({readySummary:"我负责独立测试，已阅读计划并准备就绪"})
```

缺少就绪摘要时，工具返回准备指引。插件按真实成员身份登记回复，等计划中的全部专项成员就绪后，才恢复调度并自动发送第一批委托。成员收到 `waiting` 后结束回合，等待正式任务。

任务卡规定成员的工作范围和交付方式，插件在领取时检查依赖、归属、授权和声明资源的冲突。宿主权限和工作区配置负责实际命令与文件访问。

## 5. 自动推进、验收与查看流程图

开工后，成员用 `scheduler_next` 领取或确认当前任务，完成后用 `scheduler_report` 提交摘要和产物引用，再领取下一项。依赖解除后，插件唤醒原有专项会话。

任务的 `specFile` 可引用项目内任务卡，领取结果会包含该引用及直接前置的已接受产物。任务卡应写明修改范围、测试命令和交付依据。普通任务按成员报告接受，`review:true` 的任务等待 Lead 检查真实产物和测试证据。

```text
scheduler_manage({action:"accept", target:"B2"})
scheduler_manage({action:"rework", target:"B2", feedback:"请补充错误输入的回归结果"})
```

返工保留已接受的中间产物与旧报告，新运行领取结果带入反馈。任务完成前的计划调整和其他工具用法见[接口与数据格式](接口与数据契约.md)。

v0.1.1 可在回执中显式提供文件证据，路径相对当前工作区：

```text
scheduler_report({dispatchId:"当前委托ID", summary:"接口与自测已提交", outputs:'{"api":"docs/api.md"}', files:'{"api":["docs/api.md"]}', tests:'[{"command":"node --test","exitCode":0,"stdout":"logs/tests.txt"}]'})
```

插件实际读取声明的文件并保存大小和 SHA-256。Lead 执行既有 `accept` 时重新核对；文件缺失或内容变化会阻止本次验收，原交付记录保留。普通任务仍直接交付，省略 `files` 时沿用引用模式。`tests` 是执行者自报记录，插件不会替它运行命令，也不据此自动认定测试通过。

在 Harness 文件预览中打开 `load` 返回的 `graphFile`，默认是项目内的 `.scheduler/flow.html`。主插件随状态变化维护该只读图。宽屏为三栏：左侧按任务数显示进度、就绪和当前占用，中间是居中的依赖图，点击节点或按 Enter/空格可在右侧查看依赖、资源、交付及运行记录。待验收不算完成。

搜索会淡化不匹配的节点；放大后可在画布内滚动，“适配视图”用于重新查看全图。刷新状态保留搜索、选中和缩放，并同步概览和详情。窄屏自动堆叠。升级到新布局后重新打开HTML；图只能查看，任务调整仍通过调度工具完成。

## 6. 结束并回到待机

确认成员已停止，处理所有未结束或未知运行后，由 Lead 调用以下动作。

```text
scheduler_manage({action:"unload"})
```

正在提交的工具调用结束后才能卸载。卸载会关闭本次状态存储和 HTML 更新，清理进程内等待与就绪登记，保留任务、产物和历史，再恢复待机入口。后续使用时重新“加载调度器”。

宿主重启后也回到待机。恢复已有计划需要重新加载、准备并收齐就绪回复，未结束运行沿用现有 unknown 对账方式处理。

v0.1.1 写者持有 `<状态文件>.lock`，正常卸载或退出会释放；第二个写进程会明确报出占用路径与 PID。异常终止后，先确认所有旧写者已经退出，再将残留锁移到备份位置后重新打开。保留状态和 `.bak`，不要按时间自动抢锁。只读 CLI 和图导出不占写锁；旧版写者与手工改文件不受新锁约束，更新时需停掉旧写者。

## 固定项目兼容模式

需要沿用预先配置项目的方式时，将主插件设为 `onDemand:false`，填写任务及状态绝对路径，按需要设置 `autoDispatch`。此时保留原来的四工具和首次调用绑定行为。

固定项目还可安装独立 `harness/view-bundle`。该插件也设为 `onDemand:false`，填写 `projectFile`、`stateFile` 和 `graphFile`，用于独立跟随该项目状态导图。

```yaml
- id: dynamic-task-scheduler
  disabled: false
  config:
    onDemand: false
    autoDispatch: true
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
- id: dynamic-task-scheduler-view
  disabled: false
  config:
    onDemand: false
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
    graphFile: 'D:/projects/my-app/.scheduler/flow.html'
```

## 独立命令行

离线核心仍可单独使用，以下命令在源码目录执行并沿用前面的 `$packageRoot`。

```powershell
node (Join-Path $packageRoot 'core/dist/cli.js') plan D:/projects/my-app/.scheduler/tasks.json
node (Join-Path $packageRoot 'core/dist/cli.js') check D:/projects/my-app/.scheduler/tasks.json
node (Join-Path $packageRoot 'core/dist/cli.js') status D:/projects/my-app/.scheduler/state.json
node (Join-Path $packageRoot 'core/dist/cli.js') export D:/projects/my-app/.scheduler/state.json D:/projects/my-app/.scheduler/current.html
```

`plan` 从初始化任务定义生成方案，`status` 和 `export` 读取已有状态。算法细节见[调度算法](调度算法.md)。
