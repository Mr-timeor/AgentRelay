# 快速开始

已经取得插件 ZIP 时，按[下载安装](下载安装.md)解压并安装，无需构建。本文介绍从源码生成插件及后续工作流程。下载包正进行宿主安装验收，发行附件待验收后发布。

已有 Windows Desktop 0.2.1-rc.2 的接入验证和 0.2.1-rc.3 的小规模真实协作记录，未派发任务调整已通过隔离宿主 mock 验证。跨机通用安装和其他宿主版本仍需验证。

本地规划和图导出需要 Node.js 22+、npm 和 Git。实际执行任务还需要已配置模型、支持 agent-team 服务与本地 bundle 安装的 DeepSeek Harness。

## 1. 获取源码并生成插件目录

```sh
git clone https://github.com/Mr-timeor/Multi-Agent-Dynamic-Task-Scheduler.git
cd Multi-Agent-Dynamic-Task-Scheduler
npm ci
npm run package:local
```

该命令在 `.scheduler/releases/` 生成新的独立目录，路径保存在 `.scheduler/releases/latest.json`。在项目根目录的 PowerShell 中读取它。

```powershell
$packageInfo = Get-Content -LiteralPath '.scheduler/releases/latest.json' -Raw | ConvertFrom-Json
$packageRoot = $packageInfo.directory
$packageRoot
```

构建目录包含独立核心及两个插件。

```text
<packageRoot>/
  core/dist/             # 可独立运行的规划核心和命令行
  harness/bundle/        # 调度器本地 bundle
  harness/view-bundle/   # 可选只读图本地 bundle
  fixtures/             # 示例任务
  docs/                 # 使用说明
  manifest.json         # 文件清单与构建信息
```

GitHub 仓库 URL 和下载源码的根目录用于获取源码，安装时须选择上述构建后的 bundle 目录。宿主提供插件所需的 Harness 依赖。

只体验规划与流程图时，在源码目录执行以下命令，然后用浏览器打开 `.scheduler/flow.html`。

```powershell
node (Join-Path $packageRoot 'core/dist/cli.js') graph fixtures/development.json .scheduler/flow.html
```

## 2. 准备要开发的项目

在目标仓库中准备任务 JSON 和任务卡。以下使用 `D:/projects/my-app` 作为示例，请替换为实际路径。

```text
my-app/
  .scheduler/
    tasks.json       # 任务、执行者、依赖和资源
    task-cards.md    # 任务要求、交付物和验收方法
    state.json       # 插件首次运行时创建
    flow.html        # 图插件导出
```

从[开发测试模板](../fixtures/development.json)复制任务定义，按实际项目修改。模板声明 `developer` 和 `tester` 两个专项成员，开发发布接口后实现功能，测试成员依据接口编写独立测试，两者完成后联合回归。

任务卡应明确允许修改的文件、交付物和测试命令。任务的可选 `specFile` 可以引用 `.scheduler/task-cards.md#A2`，领取结果会带入任务卡及直接前置的产物引用，专项成员按需要读取。

| 字段 | 用法 |
|---|---|
| `dependsOn` | 等待上游任务完成，或指定中间产物被接受 |
| `resources` | 声明项目相对读写范围，共享文件及构建输出也应包含 |
| `outputs` | 交付产物的名称，报告时提供对应引用 |
| `owner`、`category` | 指定执行者或匹配能力类别 |
| `review` | 为 true 时，交付后等待 Lead 验收 |
| `approval` | 为 true 时，启动前等待明确授权 |

文件资源互斥依靠执行者遵守范围。字段和状态语义见[接口与数据格式](接口与数据契约.md)。

首次使用新项目时选择一个新的 `stateFile`。已有状态继续保存的计划，修改初始化任务 JSON 不会自动替换运行中的任务。

可以先在源码目录预检任务和状态路径。

```powershell
node (Join-Path $packageRoot 'core/dist/cli.js') check D:/projects/my-app/.scheduler/tasks.json D:/projects/my-app/.scheduler/state.json
```

预检读取任务、检查依赖与路径，首次状态文件由插件运行时创建。

## 3. 安装本地 bundle 并配置 Harness

通过所用 Harness 提供的 `plugin_manager` / `install_bundle` 通道，选择 `$packageRoot` 中的 `harness/bundle` 安装调度器。需要流程图时，再安装同一构建目录中的 `harness/view-bundle`。该通道由宿主提供，具体参数以所用版本显示的工具说明为准。

本地 bundle 由目标 profile 管理依赖。安装后，在该 profile 的 `cordis.patch.yml` 中配置 agent-team 服务，并按插件 id 启用相应行。先保存现有配置备份，再将以下示例路径改为目标项目的绝对路径。

```yaml
- insert:
    - id: agent-team
      name: '@deepseek-ai/dsh-experimental-agent-team'
      config:
        maxMembers: 8
        maxTasks: 256
        maxMessageBytes: 65536
        disposalTimeoutMs: 5000
- id: dynamic-task-scheduler
  disabled: false
  config:
    leadSessionId: auto
    autoDispatch: true
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
- id: dynamic-task-scheduler-view
  disabled: false
  config:
    projectFile: 'D:/projects/my-app/.scheduler/tasks.json'
    stateFile: 'D:/projects/my-app/.scheduler/state.json'
    graphFile: 'D:/projects/my-app/.scheduler/flow.html'
```

已有 agent-team 服务时使用现有服务。图插件为可选项，按实际安装情况保留对应配置。覆盖 bundle 的行时填写 `id`、`disabled` 和 `config` 即可，`name` 由安装后的 bundle 提供。完整退出并重启 Harness 后加载配置。

## 4. 绑定 Lead 并创建专项成员

在目标项目工作区新建一个 Lead 会话，首先调用 `scheduler_status()`。`leadSessionId: auto` 会由第一次合法工具调用绑定当前 Lead，之后该 Lead 负责创建成员和管理计划。

检查初始任务、就绪项和 `autoDispatch:true`，确认读取了目标项目后，可向 Lead 发送以下提示。

```text
你是本项目的调度 Lead。
读取 .scheduler/tasks.json 和 .scheduler/task-cards.md。
核对 scheduler_status 返回的任务、就绪项及 autoDispatch。
依次创建 tester、developer 两个专项成员。
成员执行当前任务，提交真实检查依据和产物引用，再调用 next 继续。
waiting 时结束回合，依赖满足后由插件唤醒。
需要 review 的任务，检查交付和测试证据后再 accept。
遇到失败或 unknown 时核对执行现场。
完成后汇总交付物、测试结果和未解决问题。
```

沿用模板时，Lead 创建成员的工具调用为以下两项。修改执行者名称后应同步修改调用。

```text
scheduler_manage({action:"spawn", target:"tester"})
scheduler_manage({action:"spawn", target:"developer"})
```

开启 `autoDispatch` 后，成员首次 `scheduler_next` 可领取就绪任务。报告完成后可以继续领取下一项，返回 `waiting` 时结束回合，后续交付会触发插件唤醒该成员的原有会话。

这些调用通过 Harness 的聊天工具执行，成员执行真实开发与测试会使用宿主中配置的模型。

## 5. 验收、返工与查看进度

模板中的联合回归任务进入 `review` 后，Lead 检查命令、退出码与输出，再接受整项交付。

```text
scheduler_manage({action:"accept", target:"B2"})
```

需要修改时，填写具体反馈退回待验收任务。

```text
scheduler_manage({action:"rework", target:"B2", feedback:"请补充错误输入的回归结果"})
```

返工会保留已接受的中间产物与旧报告，新运行领取结果带入反馈。修改尚未接受的部分后重新提交，再由 Lead 验收。完整动作及未派发任务调整接口见[接口与数据格式](接口与数据契约.md)。

通过 `scheduler_status({taskId:"B2"})` 可以读取任务详情和完整摘要。安装图插件后，在 Harness 文件预览打开目标项目的 `.scheduler/flow.html`。支持 HTML 交互预览的宿主可搜索、缩放和查看详情，图随状态文件变化导出。

普通任务的 completed 按成员报告接受，因此任务卡应明确测试和证据要求。调用状态工具只查看必要进度，成员返回 waiting 后等待新交付。

## 6. 结束、恢复与切换项目

任务完成后确认成员停止，保留状态文件、产物和测试证据。出现 `unknown` 或宿主中断时，Lead 核对成员是否仍在执行，再通过现有对账动作处理。

内存中的等待登记在重启后需要重新建立。更换 Lead 或项目时，先确认旧成员停止，修改两个插件的项目与状态路径，然后完整重启并重新绑定。恢复原项目时使用其保存的配置和状态文件。

需要撤回本次接入时，恢复修改前的 profile 配置，通过宿主的 bundle 管理通道移除或禁用对应插件，再完整重启 Harness。

## 独立命令行

构建目录中的核心可以单独运行。以下命令在源码目录执行，并沿用前面的 `$packageRoot`。

```powershell
node (Join-Path $packageRoot 'core/dist/cli.js') plan D:/projects/my-app/.scheduler/tasks.json
node (Join-Path $packageRoot 'core/dist/cli.js') status D:/projects/my-app/.scheduler/state.json
node (Join-Path $packageRoot 'core/dist/cli.js') export D:/projects/my-app/.scheduler/state.json D:/projects/my-app/.scheduler/current.html
```

`plan` 从初始化任务定义生成方案，`status` 和 `export` 读取已有状态。命令行与图导出使用方法见[设计方案](设计方案.md)和[调度算法](调度算法.md)。
