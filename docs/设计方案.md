# AgentRelay 设计方案

AgentRelay 是任务编排与验收插件，由调度核心、Harness适配层和只读流程图组成。Harness的agent-team承载团队子代理，提供成员创建、消息投递和会话恢复，模型执行与历史也由宿主管理。AgentRelay 管理任务图、认领与交付规则、验收返工和执行事实，流程图从本地状态派生。算法细节见[调度算法](调度算法.md)。

## 三部分职责

| 部分 | 当前实现 | 接口 |
|---|---|---|
| 算法 | 硬前置DAG、就绪集、优先级／下游解锁排序、资源冲突贪心分配、顺序段融合 | normalize、diagnose、plan |
| 调配器 | 文件保存、当前任务占用、一次投递、回执、提交、可选验收和对账 | Scheduler与FileStore |
| 可视化 | 竖向拓扑分层SVG（阶段自上而下、同阶段按类别分组）、节点卡片详情、等待原因、段和交付点列表、搜索缩放 | renderGraph |

Harness适配层校验合法调用者，并调用宿主服务创建成员和发送消息。核心不导入宿主包；一个Lead绑定一个团队，多视图只有读取能力。

## 成员与上下文

适配器通过 `agentTeams.spawnTeammate` 创建当前 Lead 的持久团队子会话，默认 `context:"fresh"`、provider 为 `spawn`，不复制父聊天历史。仅复用当前团队中同名成员，不按普通对话标题接管会话。

子代理按宿主规则继承模型路由、工作目录与预设组合；项目规则由宿主加载。业务要求通过计划、任务卡、前置交付引用和摘要传递，成员后续执行使用自己的会话历史。

调度管理动作和团队增员仅限 Lead。插件没有额外屏蔽所有原生委派工具，不能据此宣称全面禁止嵌套子代理；宿主原生委派还受其工具配置与深度策略约束。

## 执行方式

规划沿当前可连续完成的任务形成执行段。遇到外部前置、review检查点或段长上限停止。预测不修改状态，未来任务不提前占用资源。

默认手动模式首次由Lead派发；开启autoDispatch后，首次next可直接领取就绪任务，交付会触发给等待成员的委托。专项执行者完成当前任务后再next领取，不要求Lead逐项转述。中间产物及时提交，普通产物直接接受，明确声明review的产物才等待验收。

所有真实开始都重新检查依赖、授权、执行者和资源。运行记录保存结果与失败。文件／目录声明做粗粒度冲突判断；共享工作区没有文件系统隔离。

## 最小选择

TypeScript编译为ESM，核心使用Node.js标准库。单宿主进程串行写入JSON快照，默认段长为4，回执等待为120秒。

模型通过4个工具领取任务、提交结果、查询状态和管理计划，内部ID由程序处理。review和approval只用于明确设置的节点。

计划变化通过追加任务或调整尚未派发的任务处理。已有运行记录的任务可以返工或以新增任务修订，原有交付和运行历史继续保留。已接受产物的引用在后续返工中传给执行者。

只读图输出独立HTML，可在浏览器或宿主文件预览中打开。图按依赖阶段排列任务，并随状态文件变化重新导出。

## 当前限制

单个安装实例绑定一个项目和一个Lead。资源声明协调共同遵守文件范围的执行者，共享工作区中的实际文件操作仍由开发流程负责。宿主重启后，未结束运行进入unknown，需要Lead确认执行情况后继续。

当前支持任务完成和指定产物接受两种硬前置，按事件重新计算完整任务图。工期预测、软依赖、自动上下文重建和跨进程恢复尚未实现。效率、费用和上下文压缩收益需要在实际项目中评估，已有功能及安装步骤见[快速开始](快速开始.md)。
